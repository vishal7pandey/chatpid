# CPID-12 — CypherRAG is not truly read-only

Status: spec-approved · Risk: high · Jira: CPID-12

## Repro

Environment: main @ c21ef34 (before the fix), Windows, Python 3.14, recording fake driver (no Neo4j available here: Docker daemon is down).

1. The LLM (or a prompt-injected question) produces a statement the regex blocklist does not know, e.g. `CALL gds.pageRank.write('g', {writeProperty: 'pr'})`, `CALL custom.writeProc('x')`, `STOP DATABASE neo4j`, `ALTER USER neo4j`, `GRANT ROLE admin TO bob`.
2. `execute_cypher(driver, <statement>)` passes `_validate_read_only` and runs it in a default (read-write) session.

Automated repro (fails on the old code, passes after the fix):

- `.venv/Scripts/python.exe -m pytest tests/test_cypher_rag_readonly.py -q`; before the fix 11 tests failed, e.g. `DID NOT RAISE ClientError` for the evading statements and `assert [{}] == [{'default_access_mode': 'READ'}]` for the session mode.

Reproducibility: always (at the driver-call level). The server-side refusal itself needs a live Neo4j (see AC2 and the opt-in test).

## Expected

All Cypher generated by the agent runs in a read transaction, so the database refuses writes even if the regex misses them; the regex stays as a second layer (ticket AC1, AC2, AC3).

## Actual

`chatpid/cypher_rag.py` opened `driver.session()` without an access mode in `execute_cypher` and in the two schema-introspection helpers, and `execute_cypher` ran `session.run(cypher)` in a write-capable auto-commit transaction. The only protection was `_validate_read_only`, a regex blocklist (documented evasions above).

## Root cause (with evidence)

- Where: `chatpid/cypher_rag.py`, `execute_cypher()` and the `driver.session()` calls in `get_graph_schema()` and `_get_label_list()`.
- Why it fails: write protection depended on pattern-matching model output instead of database-enforced access mode.
- Introduced by: always present.
- Evidence: the failing tests above; `tests/test_cypher_rag_readonly.py::test_regex_gaps_are_real_so_the_database_layer_is_needed` shows the regex lets the statements through.

## Blast radius

- Only `execute_cypher` runs LLM-generated text; the other `driver.session()` uses in the repo (`api.py`, `context_rag.py`, `path_rag.py`, `vector_rag.py`, `semantic_enrichment.py`, `ingest.py`) run fixed, parameterised queries written by us. `ingest.py` and `semantic_enrichment.py` legitimately write. The read-only fixed queries in `context_rag`, `path_rag`, `vector_rag` and `api.py /graph` could also use `READ_ACCESS` as hygiene; out of scope here (not model-generated).
- `scripts/08_cypherrag_spike.py` calls `execute_cypher`; it is read-only by design and unaffected.
- Related regex weakness, not changed: `\bSHORTESTPATH\b` blocks a legitimate read function, `\bSET\b` can false-positive on string literals.
- The compose file runs Neo4j with a known dev password (ticket note); a read-only Neo4j user for this path is the stronger fix and needs an owner decision (see Risks).

## Regression criterion (AC1)

AC1: `execute_cypher` opens its session with `default_access_mode=READ_ACCESS` and runs through `session.execute_read`; every session in `cypher_rag.py` is read-only (`::test_execute_cypher_opens_a_read_access_session_and_a_read_transaction`, `::test_every_session_the_module_opens_is_read_only`, `::test_cypher_rag_pipeline_runs_the_generated_query_in_a_read_transaction`).

AC2: a write that evades the regex is rejected at the driver layer: with a fake driver that models a server refusing writes in read-only sessions, six regex-evading statements raise `ClientError` and no write transaction is ever opened; a control shows the same fake accepts the statement in a default session; bypassing the regex entirely still raises; the pipeline falls back instead of writing (`::test_write_that_evades_the_regex_is_rejected_by_the_read_only_database_layer` and neighbours). The fake only models the server. Real proof needs Neo4j: `tests/test_cypher_rag_live.py` (opt-in, `CHATPID_LIVE_NEO4J=1`, steps in its docstring) attempts a `CREATE` through `execute_cypher` with the regex bypassed and asserts Neo4j refuses it and nothing was written. It was NOT run here (no Neo4j); it is skipped by default and in CI.

AC3: the existing CypherRAG tests pass. One test, `test_legitimate_match_return_passes`, had its mock plumbing changed (MagicMock cannot execute the `execute_read` callback; it now uses the recording fake driver); its assertion is unchanged.

## Fix constraints

Same public signatures and return shapes; regex kept; no new dependency (`READ_ACCESS` and `execute_read` exist in neo4j >= 5.22, locked at 6.2.0). `tests/fakes.py` gains `session(**config)`, `execute_read/execute_write` and an optional `write_detector`, backwards compatible.

## Risks

High: security control on LLM-driven database access (security.md: human review; delegated here). Rollback: revert the commit. Open for the owner: a dedicated read-only Neo4j user/role for the query path (infrastructure/credentials, not done here).
